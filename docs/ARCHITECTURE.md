# Архитектура

```mermaid
flowchart LR
  UI[pywebview UI (web/ + api.py мост)] --> App[Application services]
  App --> Store[(Project SQLite + immutable source copy)]
  App --> Formats[Format importers / writers]
  App --> Queue[Persistent cancellable task queue]
  Queue --> Seg[Segmenter + context + glossary]
  Queue --> Proc[Spawned inference process]
  Proc --> Adapter[GGUF adapter: llama-cpp-python]
  App --> Download[Consent + pinned model download]
  App --> Device[Hardware probe + resource recommendation]
  App --> Custom[Confirmed local GGUF import + SHA-256]
  Download --> Stage[.part → size/SHA/GGUF check → atomic activation]
  Queue --> Store
  Formats --> Store
  Download --> Models[(LOCALAPPDATA\\DotLingo\\models)]
  Custom --> Models
```

## Слои

- `formats.py`: importer/writer boundary и нормализованные `ParsedDocument`/`Block`; никаких UI-типов.
- `segmentation.py`, `glossary.py`: чистые функции. Segmentation ограничивает порции; имена из глоссария защищаются уникальными маркерами на каждое совпадение.
- `storage.py`: отдельная SQLite база на проект (`WAL`, `synchronous=FULL`), immutable source copy, SHA-256, parsed tree, переводы по целевому языку, очередь, обнаруженный исходный язык, события и экспортные записи. Задача фиксирует модель, направление, контекст и правила на момент постановки в очередь.
- `languages.py`: названия языков и список кодов, доступных в выборе для каждой модели. Это интерфейсная выборка из заявленной поддержки, а не гарантия качества языковой пары.
- `task_queue.py`: один последовательный worker на проект, блоки сохраняются фрагментами; остановка завершает дочерний inference процесс. При режиме автоопределения модель классифицирует до 4000 символов документа один раз, результат кэшируется в проекте. Если язык не распознан, prompt просит модель определить его для каждого фрагмента. UI видит event dict, не engine.
- `engine.py`: отдельный Windows spawn process для DLL/RAM ошибок; GGUF magic до старта, timeout, cancel/pause. Число GPU-слоёв задаёт очередь по свободной VRAM. Если старт на GPU падает из-за памяти, процесс один раз поднимается заново на CPU, окно укорачивается до 4096, батч до 256. Перед импортом регистрируются каталоги `nvidia/*/bin` из site-packages. Реальный прогон с весом на Windows не выполнен.
- `model_download.py`, `models.py`: каталог с закреплёнными artifact revision/size/hash, allowlisted HTTPS, проверка пути/перенаправления/range/size/SHA/magic; staging переименовывается в активный вес после проверки. Файл GGUF загружается как данные, произвольный Python из модели не исполняется.
- `market.py`: по кнопке читает фиксированный список репозиториев Hugging Face (карточки и дерево файлов, не веса). В список попадают одиночные GGUF кванты Q4/Q6. Перед скачиванием ревизия, размер и SHA-256 сверяются ещё раз. Реестр скачанных файлов - `market_models.json`.
- Пользовательские GGUF хранятся в `models/<custom-id>/model.gguf`; реестр содержит локальные метаданные, список языков задаёт пользователь, а совместимость и качество не подтверждаются. Импорт копирует файл только после отдельного подтверждения, сверяет GGUF magic, размер и SHA-256; исходник не меняется.
- `hardware.py`: RAM и свободный диск из psutil; NVIDIA имя, полный и свободный VRAM через `nvidia-smi`, если он доступен; llama backend проверяется независимо. Кэш показывается сразу, на каждом запуске замер повторяется. Рекомендация и вердикт «не хватает ресурсов» сравнивают расчётную RAM со всей памятью устройства с запасом 1 ГБ и со свободным местом на диске; это оценка размещения, не качества. Свободная RAM на вердикт не влияет. CPU-потоки настраиваются автоматически с пределом 8 и одним оставленным логическим потоком. GPU-слои включаются, только если свободная VRAM дискретной карты покрывает расчёт и запас 1.4 ГБ. На CPU контекст не длиннее 4096, батч 256; с GPU батч 512.
- `runtime_install.py`: по явной кнопке ставит в текущий интерпретатор CPU-колесо `llama-cpp-python==0.3.35` или, для дискретной NVIDIA и Python 3.10-3.12, сначала `nvidia-cublas-cu12` и `nvidia-cuda-runtime-cu12`, затем CUDA-колесо cu124. Первый ненулевой код pip останавливает цепочку. Собранный Setup.exe колесо не меняет.
- `updater.py`: для запуска из git-клона сравнивает HEAD с `origin/main`. Проверка при старте только читает remote. Кнопка делает fetch, `reset --hard` и `pip install -e ".[pdf]"`. Локальные правки требуют подтверждения. Неотслеживаемые файлы и каталог данных не стираются. Собранный Setup.exe эту схему не использует.
- `app.py`: тонкая точка входа. Создаёт окно pywebview 1280x820 (минимальный размер 1020x680) с `js_api`-мостом и локальной HTTP-раздачей `web/`; `http_server=True` обязателен, потому что ES-модули не загружаются с `file://` (CORS). Параметры: `--data-dir`, `--smoke-test`. При ошибке старта (отсутствие WebView2) печатает подсказку и показывает MessageBox; закрытие окна вызывает `closeGracefully` моста.
- `api.py`: мост `js_api` между web UI и ядром. Методы camelCase, ответы в едином конверте `{ok, data}` либо `{ok: false, error, code}`. Длительные действия (импорт документов, загрузка и проверка модели, импорт своего GGUF, детект оборудования) выполняются в daemon worker-потоках и сразу возвращают `{started: true}`; результаты доставляются push-событиями через `evaluate_js` в `window.DL.push_event`: `task_event`, `download_progress`, `hardware_detected`, `documents_imported`, `download_done`, `model_verified`, `custom_model_imported`, `export_done`, `runtime_install_progress`, `runtime_install_done`, `update_status`. Ранее UI опрашивал события через Tk `root.after(150)`; polling удалён, обновления приходят только push-событиями. Нативные диалоги выбора файлов - через `window.create_file_dialog` моста.
- `web/`: статический vanilla JS на ES-модулях, без сборочного шага. `index.html`; `styles/` (`tokens` - тема через атрибут `[data-theme]` на `<html>`, `base`, `components`, `shell`, `pages-work`, `pages-library`); `js/` (`main`, `bridge` - вызовы моста и `push_event`, `store`, `router`, `components`, `icons`); `js/pages/` (`chat`, `projects`, `documents`, `review`, `queue`, `models`, `glossary`, `settings`, `wizard`). Python-модуль `theme.py` удалён: темы задаются только CSS.
- `paths.py`, `preferences.py`: бинарники приложения, проекты и веса физически разнесены. Сборка предполагает per-user установку под `%LOCALAPPDATA%\Programs\DotLingo`.

## Поток документа

1. Импорт и проверка формата → нормализованные блоки с locator.
2. Отдельная копия исходника с SHA-256; исходные байты не используются как место для перевода.
3. Сегментация абзацев около sentence/whitespace границ. При постановке задачи лимит знаков берётся из окна модели: 700 при 2048, 1600 при 4096 и 2400 при большем окне. Вызов без лимита по-прежнему режет на 1100. Длинное слово делится по лимиту, каждый байт источника сохраняется.
4. Для каждого целевого языка создаётся отдельная задача со снимком направления и настроек проекта.
5. Промпт получает направление, контекст проекта, правила и глоссарий. Стабильная инструкция стоит в начале, а память книги, недавний перевод и источник идут в конце: так llama.cpp может переиспользовать общий префикс. Окно недавнего перевода - 480, 1200 или 2400 знаков по размеру контекста. При окне от 4096 каждые 20 фрагментов короткая память книги обновляется и сохраняется в задаче. До четырёх соседних целых блоков уходят одним запросом; продолжение разрезанного абзаца переводится отдельно. Если в ответе не столько абзацев, сколько было в запросе, эти фрагменты переводятся по одному. Marker изменён или потерян → fragment error, не записываем его как завершённый.
6. Сегмент сохраняется в SQLite немедленно. Завершённая задача атомарно обновляет перевод документа для своего целевого языка.
7. Редактор показывает исходный блок отдельно от перевода; язык выбирается в панели проверки. Export writer использует только выбранный целевой язык, пишет staged отдельный файл и делает `os.replace` после успешной записи.

## Очередь и восстановление

Статусы: `queued`, `running`, `paused`, `cancelled`, `interrupted`, `failed`, `complete`. Для завершённых фрагментов хранится отдельная строка. При открытии проекта `running` переводится в `interrupted`; queued-задачи, ранее явно созданные пользователем, возобновляются. Остальные требуют кнопки «Продолжить / повторить». Направление каждой задачи не меняется при последующей правке настроек проекта. Повтор с другой моделью обнуляет части задачи; существующие переводы остаются видимыми до успешного завершения нового задания для того же языка.

## Runtime adapters

Первый адаптер: официальные GGUF Hy-MT2 (1.8B Q4_K_M, 1.8B Q8_0, 7B Q4_K_M) через `llama-cpp-python`. Каталог указывает adapter id и весовой формат; safetensors и Marian в этот loader не передаются. Промпт Hy-MT2 - одна user-реплика по карточке модели, без system prompt и без `/no_think`. Сэмплинг берётся из карточки. Будущие адаптеры: CTranslate2 для Marian/OPUS-MT и отдельный Transformers adapter, если появится схема без исполнения произвольного кода. TranslateGemma и STQ-кванты Hy-MT2 в загрузку не входят.

Пользовательский импорт принимает только локальный GGUF и использует тот же chat-completion интерфейс с общим промптом переводчика. Для него `/no_think` и Qwen-стопы не передаются, GPU по умолчанию не включается: у файла нет оценки VRAM. Совместимость chat template проверяется только при запуске. Языки и контекст задаёт пользователь; это не проверенные характеристики модели.

## Расширение на другие ОС

Доменные функции и SQLite слой Qt-free. Для macOS/Linux достаточно заменить `paths.py`, отдельный native bootstrap/package и backend-профиль; код и настройку Windows Setup отдельно собирать для каждой ОС. Текущий UI и установщик проектируются первым делом для Windows 10/11 x64. Кроссплатформенная поставка не проверена.
